# 并发编辑与自动保存

同一页可以在两个会话里打开。后提交的人如果还拿着旧版本，保存会停下来，必须选择覆盖或放弃并刷新。静默地用后一次写入盖掉先一次写入已经去掉。

## 版本号

`Page.revision` 是整数，新建页面从 0 开始。每次成功保存标题、图标、封面、可见性、置顶或正文时加 1。客户端每次 `PATCH /api/pages/:id` 都带上自己打开或上次保存时看到的 `baseRevision`。请求体里没有这个字段时，校验直接失败，不会落库。

服务端在同一个事务里做两件事：

1. `updateMany`，条件是页面 id，并且（没有选择覆盖时）`revision` 等于 `baseRevision`。命中则把 `revision` 加 1，并写上新的页面字段。
2. 只有这一步刚好更新了 1 行，才删除并重建块。没命中时块保持原样。

没命中就返回 409，正文是「这篇页面在别处被修改了」，并带上服务器上的最新页面。收藏和侧栏里的移动只改别的表或 `parentId` / `position`，不增加这个版本号，所以不会把正在写的人误判成冲突。

选择覆盖时，请求带 `overwrite: true`。这时只按页面 id 更新，版本号仍然加 1。这是旧版本能够写入的唯一路径。

## 冲突时的两个选择

409 不记成普通的保存失败，也不自动重试。状态变成「发现冲突」，自动保存暂停，对话框（`data-testid="conflict-dialog"`）留在页面上，点遮罩或按 Esc 都关不掉。

- **放弃并刷新**（`conflict-discard`）：重新 `GET /api/pages/:id`，用服务器上的页面替换本地标题和正文。
- **覆盖**（`conflict-overwrite`）：用当前本地内容再保存一次，并带上 `overwrite: true`。

同一个标签页里的保存是串行的。第一次请求还在飞时内容又变了，就等它返回，把新的版本号接过来，立刻再提交最新内容。这样自己的连续输入不会把自己判成冲突。另一个标签页若在中间写成了，后一次提交会收到真正的 409。

离开页面时的兜底保存也带着 `baseRevision`。已经处于冲突时不再发这次请求，避免用旧版本再写一次。

## 自动保存与失败

编辑后 500 毫秒合并成一次保存。连续输入只会在停顿后提交。

保存失败时，状态写成「保存失败」，并弹出服务端返回的错误，缺省文案是「保存失败」。旁边出现「重试」（`data-testid="save-retry"`），再提交同一次内容。冲突不是这种失败，没有这个按钮。

## 测试

`e2e/conflict-save.spec.ts` 用两个 Nash 会话覆盖下面的情况，全量端到端里 4 个都通过：

| 场景 | 结果 |
| --- | --- |
| A 改标题并保存，B 还拿着旧版本再改标题 | B 收到 409 和冲突对话框。B 选择放弃并刷新后，标题是 A 写的「先写的标题」，刷新后仍在 |
| A 先写正文，B 再写正文并选择覆盖 | B 的保存成功。A 刷新后看到「后写的正文」 |
| A 改完正文又改了标题，B 拿着更早的版本来写 | B 收到 409。B 不做选择时，A 的标题「必须留下」和正文都还在 |
| 连续输入「节流」 | 800 毫秒内只有 1 次 PATCH。把下一次保存模拟成 500 后，出现「保存失败」和重试；点重试后状态回到「已保存」，刷新后正文还在 |
