# 外观跟随账号

第四轮阶段 3。登录之后，跟随系统、浅色、深色记在账号上，换浏览器也会跟着走。没登录的页面仍只用这台浏览器的存储。

## 规则

账号上的选择存在 `UserPreference.theme`。空着表示这个账号还没选过。一旦写成 `system`、`light` 或 `dark`，就算明确选过，包括「跟随系统」。

- 登录或注册时，如果账号已经有选择，用账号的，并把这台浏览器的 `folio-theme` 改成同一个值。两边不一样时，账号赢。
- 账号还没选过，而这台浏览器里已经有 `system`、`light` 或 `dark`：把浏览器里的选择写入账号。这是第一次登录时保留这台电脑上已有选择的方式。
- 两边都没有：继续跟随系统，不往账号里写。之后换一台没有本地选择的电脑，仍跟随那台电脑的系统。
- 没登录时，包括登录页和匿名打开的分享页，只读写这台浏览器的 `localStorage`。请求账号接口会得到 401，选择不会上传。
- 退出登录不删这台浏览器里的值。登录页先按它显示。下次登录如果账号上是另一种，再改成账号的。

侧栏、登录页和分享页用的是同一个开关。顺序仍是跟随系统、浅色、深色，再回到跟随系统。

## 怎样避免先闪一下错误的颜色

整页加载时，根布局在服务端读出当前登录用户的选择，写进页面最前面的脚本。脚本在绘制前执行：

- 账号上有选择：立刻套用，并写入这台浏览器。系统是深色、账号是浅色时，第一次绘制就是浅色，不会先按系统画成深色再改。
- 账号上没有，或当前没登录：沿用这台浏览器里的值；也没有的话跟随系统。这种情况下脚本不改 `localStorage`。

从登录页进去是客户端跳转，那段脚本不会重跑。登录和注册的响应里带回最终选择，跳转前就套用。工作区打开时，本地值已经和账号一致。

已经开着的页面不会自己去拉另一台设备刚改的选择。下一次整页加载会用账号上的新值。

## 数据库

`theme` 是可空字符串，加在原来的 `UserPreference` 上。本地 SQLite 和 PostgreSQL 都靠 `prisma db push` 补上这一列。没有新增迁移 SQL。仓库里已有的 SQLite 迁移不要拿到 PostgreSQL 上执行。重新播种时，两种数据库都会先删掉 `UserPreference`，避免上一轮留下的外观被带进新数据。

侧栏展开状态仍写在同一行的 `sidebar` 里。保存外观只更新 `theme`，保存侧栏只更新 `sidebar`。

## 如何验证

单元测试不连数据库。原先两条仍在：没选择时跟随系统，以及浅色、深色、再回到跟随系统。新增两条：账号和本机不一致时用账号，账号为空才收下本机的选择；启动脚本在有账号选择时先画那个颜色，并覆盖本机里相反的值。没登录时脚本不改存储。

端到端保留原来的两条：系统为深色时登录页跟随系统，手动选择在刷新后还在；匿名分享页用同一个开关。新增三条：

1. Nash 在一个浏览器里选浅色。另一个浏览器系统是深色，登录后直接是浅色。刷新得到的页面里，绘制前脚本写的是账号的 `light`。
2. 账号是深色时，另一台浏览器先把本地改成浅色。登录后改回深色，本地存储也改成深色。
3. 注册前在这台浏览器里选浅色。新账号记下浅色。另一个系统为深色的浏览器登录后仍是浅色。

浅色和深色的 axe 检查没有改断言。

## 限制

- 外观跟账号走，不跟某一个工作区走。
- 账号里还没写过选择时，一台新浏览器会跟随它自己的系统，直到某台浏览器上的明确选择被保存。
- 已经打开的页面要等下一次整页加载，才看得到别的设备刚改的选择。
- 退出后，这台浏览器仍留着上次的值。
- 损坏的存储值当成还没选过。
