# 大页面与深页面树

测量脚本是 `scripts/large-page.bench.ts`，用 `npx playwright test --config playwright.bench.config.ts` 单独跑。它不在 `npm run test:e2e` 里，避免每次端到端都创建 320 个块。

脚本登录后新建一个工作区，写入 320 个段落，再串起 15 层页面（第 1 层到第 15 层）。编辑器数字来自一次热刷新：先打开页面，再 `reload`，等第 320 个块出现。加载时间用这次刷新的 `performance` navigation 条目。编辑和拖拽在客户端水合完成之后才开始计时，避免把水合算进按键。

## 第一次测量里看到的问题

第一次测量在产品工作区里进行，第 320 个块一出现就开始计时，水合还没结束，按键时间里混进了整页重连：

| 项目 | 数值 |
| --- | --- |
| 块数 | 320 |
| 热刷新到第 320 块可见 | 1346 ms |
| 导航 domContentLoaded / load / response | 952 / 1240 / 862 ms |
| 合成输入到两帧之后 | 345 ms |
| 真实按键 | 406 ms |
| 把第 3 段拖到第 1 段前面 | 1233 ms |
| 编辑期间长任务 | 11 次，最长 332 ms |
| 打开第 15 层 | 688 ms，15 层都可见 |
| 把第 15 层拖到第 14 层前面 | 418 ms |

按键约 345–406 ms，拖拽时长任务到 332 ms。页面树 15 层可以打开和拖动，不是这次要处理的部分。

## 优化

慢在编辑器每次按键都重做整页：

- 每次 `blocks` 变化都对全部文本框读 `scrollHeight`。现在只有焦点在块输入框里时才量那一个；没有焦点时（初次布局）才量全部。
- 每次按键都重绘 320 行。行用引用比较跳过未改动的块。引用块和折叠块还会比较子块引用，子块变化时父行仍会更新。
- `withPositions` 以前每次都复制每一个块，比较因此失效。现在字段没变的块保持原对象。
- 未激活行不再画出加号和握把图标，按钮仍占 24×24，拖拽拿得到位置。

## 同一套测法的前后对比

下面两次都在新建的工作区里，用同一脚本，并且等 React 挂上页面节点、再过两帧和 50 ms 之后才计编辑时间。优化前是当时的编辑器，优化后是上面的改动。

| 项目 | 优化前 | 优化后 |
| --- | --- | --- |
| 块数 | 320 | 320 |
| 热刷新到第 320 块可见 | 1332 ms | 1027 ms |
| 导航 domContentLoaded | 948 ms | 623 ms |
| 导航 load | 1248 ms | 964 ms |
| 导航 response | 894 ms | 539 ms |
| 合成输入到两帧之后 | 137 ms | 16 ms |
| 这次输入的长任务 | 1 次，127 ms | 0 |
| 真实按键 | 286 ms | 25 ms |
| 把第 3 段拖到第 1 段前面 | 1260 ms | 257 ms |
| 这次拖拽的长任务 | 9 次，最长 253 ms | 0 |
| 打开第 15 层 | 626 ms | 612 ms |
| 可见层数 | 15 | 15 |
| 把第 15 层拖到第 14 层前面 | 314 ms | 313 ms |

优化后的输入留在了块里。拖拽的 257 ms 含指针分 12 步移动的时间，期间没有长任务。15 层页面树的加载和拖拽与优化前同一量级，没有再改树的实现。

热刷新仍大约 1 秒，其中文档响应占 539 ms。这是开发模式一次返回 320 个块的开销，编辑时已经没有长任务。

## 生产构建

同一脚本再跑两遍，服务器改为 `next build` 之后的 `next start`（`playwright.bench.prod.config.ts`）。计时方式不变：热刷新后等到第 320 个块可见，文档响应取 navigation 的 `responseEnd - requestStart`。

| 项目 | 第一次 | 第二次 |
| --- | --- | --- |
| 热刷新到第 320 块可见 | 130 ms | 165 ms |
| 文档响应 | 42 ms | 59 ms |
| domContentLoaded | 55 ms | 75 ms |
| load | 58 ms | 77 ms |

两次都在 200 ms 内看到全部 320 个块，文档响应不到 60 ms。生产模式没有再出现需要处理的加载问题，因此没有为这一项再改实现。开发模式里那约 1 秒是开发服务器的开销。
