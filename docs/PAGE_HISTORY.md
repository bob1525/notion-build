# 页面历史

第三轮阶段 3。自动保存成功之后，按人和时间把正文收成快照。可以打开历史列表，看时间和编辑者，预览旧版本，并一键恢复。恢复走原来的页面保存：版本号加一，别人抢先保存时返回 409。

## 做了什么

每次正文保存成功，都会在同一笔事务里决定要不要记一条 `PageSnapshot`。快照里有标题、图标、封面和全部块（含嵌套、格式、图片地址）。可见性、置顶和作者不放进快照。恢复时这三项保持页面上的当前值，所以恢复不能把公开页改回私有，也不能改权限。

页面工具栏有「历史」。列表按最后写入时间从新到旧，每条显示本地时间和编辑者。点一条可以预览当时的标题和正文。能编辑的人看到「恢复这个版本」。

恢复请求带上当前的 `baseRevision`。服务端把它交给原来的 `updatePage`：版本号匹配才写入，并加一。不匹配则 409，页面上弹出原来的冲突对话框。选覆盖会带 `overwrite` 再恢复一次；选放弃并刷新则保持别人刚保存的内容。恢复成功后一定会新开一条快照，编辑者记成执行恢复的人，即使这次恢复落在 5 分钟窗口内。

复制页面不复制历史。副本从自己的第一次正文修改开始记。

## 快照怎么合并

自动保存大约每 500 毫秒一次。若每次按键都插一条，历史会很快被中间过程填满。规则在 `src/lib/page-history.ts`：

- 这一页还没有快照：新建一条。
- 和最近一条的标题、图标、封面、正文完全一样：跳过。空转的自动保存不会把 5 分钟窗口往后推，编辑者仍是上次真正改过正文的人。
- 同一人，并且距离最近一条的最后写入不足 5 分钟：改写这一条，时间改成这次保存。连续打字会一直延长这条，中间过程不保留。
- 同一人，停满 5 分钟再保存：新开一条。满 5 分钟整也新开。
- 换一个人保存，只要正文有变化：马上新开一条，不等 5 分钟。
- 时钟倒退：新开一条，避免窗口永远合并不结束。
- 恢复：总是新开一条。

只改可见性或置顶时，正文没有变，不记快照。

历史从第一次改动标题、图标、封面或正文之后开始。刚建出来、还是空白的那一页不会另存一条。

窗口长度是 `PAGE_HISTORY_COALESCE_MS`，5 分钟。对话框里的说明用的是同一个数。

## 第四轮阶段 2

历史列表和预览里的时间用观看者浏览器的时区，并写出偏移，例如 `11月28日 00:30（UTC+08:00）`。同一时刻在上海是 28 日 00:30，在 UTC 仍是 27 日 16:30。页头「编辑于」和工作区列表仍用 UTC，没有偏移，那两处这一阶段没有改。

公开或公开只读的页面，分享地址上有「历史」。列表和预览走 `/api/share/[pageId]/history`，不要求登录。私有页这个接口返回 404，和分享页本身打不开是同一条规则。页面一旦能被分享，已经记下的快照也会出现在这条列表里；改回私有后，分享地址和这个接口都不再返回它们。

恢复没有新接口。分享页上只有能编辑这篇的登录成员看得到恢复按钮，请求仍是原来的 `POST /api/pages/[pageId]/history/[snapshotId]/restore`，经 `updatePage` 检查版本号。版本号旧了返回 409，可以选择覆盖或放弃并刷新。只读成员、未登录的人，以及登录了但不属于这个工作区的人，在分享页上只能看。未登录恢复得到 401，只读成员得到 403，工作区以外的登录用户得到 404。

## 谁能看，谁能恢复

历史接口都要登录。能看这篇页面的人就能看历史，和 `canViewPage` 一致：

- 作者始终可以看，也可以恢复。
- 公开可编辑的页面，工作区成员可以看，也可以恢复正文。
- 公开只读的页面，工作区成员可以看列表和预览，不能恢复。工作区所有者可以恢复，因为所有者也能改正文。
- 私有页只有作者能看历史。工作区所有者看不到别人的私有页，也就看不到它的历史。
- 公开链接上也能看历史。能通过分享地址打开的页面，未登录的人、以及登录了但不在这个工作区里的人，都能看列表和预览，不能恢复。私有页的分享地址打不开，公开历史接口也返回 404。
- 分享页上，能编辑这篇的登录成员可以看到「恢复这个版本」。恢复仍交给原来的 `updatePage`，版本号不对时返回 409。只读成员在分享页上没有恢复按钮，恢复接口返回 403。未登录调用原来的历史接口和恢复接口会得到 401。

只读成员点「历史」会看到「你只能查看历史，不能恢复。」恢复接口对他们返回 403。分享页上的只读访客看到同一句。

还有没保存完的本地修改时，恢复会停住，等自动保存完成后再点。避免一次点击把没写完的内容和所选历史搅在一起。

## 清理

没有定时任务。每次写入快照之后，如果这一页超过 50 条，按最后写入时间删掉最老的，只留最新的 50 条。时间相同则留 id 较大的那条。

单条快照的块 JSON 超过 40 万字符就不记这一条。页面本身照常保存。已经记进去的短快照不会因为这一次太大而被删掉。50 条和 40 万字符同时生效。一页在上限下大约最多 50 × 40 万字符。

删除页面会级联删掉它的快照。播种清库时，SQLite 和 PostgreSQL 都会在删页面和用户之前删掉 `PageSnapshot`。

## 数据库

`schema.prisma` 增加了 `PageSnapshot`。本地 SQLite 和线上 PostgreSQL 用的是同一份模型。`prisma db push` 会在两种数据库上建表。仓库里的 `provider` 仍是 sqlite，PostgreSQL 继续由 `scripts/db-prepare.ts` 生成 `schema.postgres.prisma`，不把这份生成文件提交。

另外有一份迁移：

- `prisma/migrations/20261127120000_page_snapshots/migration.sql` 是 SQLite 写法，用 `DATETIME`。不要在 PostgreSQL 上执行它，也不要对这些库跑 `prisma migrate deploy`。
- `scripts/apply-page-history-migration.ts` 按当前数据库选择语句。SQLite 用 `DATETIME`，PostgreSQL 用 `TIMESTAMP(3)`。两边都是 `CREATE TABLE IF NOT EXISTS`，表已经在时什么都不做。`npm run db:push`、`db:reset`、`db:deploy`、`setup` 和 `test:e2e` 都会在 `db push` 之后跑它。

已经部署过的库，下一次 `npm run db:deploy` 会补上这张表，不用手工删库。

## 如何验证

单元测试不连数据库，锁住合并窗口、换人新开、恢复强制新开、超长跳过、50 条清理、只读能看不能恢复，以及两种数据库的建表 SQL。

端到端在浏览器里做三件事：

1. 同一人连续改两次标题。页面版本号至少到 2，历史仍是 1 条，预览是后一次的标题。
2. Nash 写下正文，Mia 在公开可编辑页改成另一段。Nash 恢复旧正文，历史变成 3 条；再恢复 Mia 的版本，历史变成 4 条。用过期的 `baseRevision: 0` 调用恢复，返回 409，刷新后仍是 Mia 的正文。
3. 私有页上 Mia 读历史得到 403。改成公开只读后，她能打开列表和预览，页面上没有恢复按钮，恢复接口返回 403。作者仍能看到恢复按钮。
4. 浏览器时区设成 `Asia/Shanghai` 后，历史条目显示 `UTC+08:00`，并和 `formatZonedDateTime` 的结果一致。
5. 公开只读页的分享地址上，未登录的人能看列表和预览，没有恢复按钮，恢复接口返回 401。只读成员返回 403。作者用过期版本号恢复返回 409，用当前版本号可以恢复。页面改回私有后，分享地址打不开，公开历史接口返回 404，成员接口仍是 403。

块里已经有文字时，Playwright 的 `fill` 会把新文字接到旧文字前面。恢复那条端到端改为先全选再插入，并立刻检查输入框的值。

## 发现的问题

- 第四轮之前，列表上的时间用的是 UTC，和页头「编辑于」一样。现在列表和预览用观看者的本地时区，并标出偏移。页头和工作区列表仍是 UTC。
- 5 分钟内同一个人的中间过程会被收成最后一版，恢复不回去。
- 正文 JSON 超过 40 万字符的那一次保存不会留下快照。页面仍保存成功。
- 恢复不改可见性、置顶和作者。复制出来的页面没有旧历史。
- 第四轮之前，公开链接不提供历史。现在能打开的分享页可以看历史。私有页的历史仍只有作者能看，分享接口不会把私有页的快照交出去。
- 工作区所有者可以恢复别人的公开只读页，因为所有者也能改那篇正文。普通只读成员不行。
- 清理发生在下一次写入时。没有后台任务去扫旧数据。
- 块输入框在已有文字时，自动化的 `fill` 会把新字接到前面。手工输入和「先全选再替换」是正常的。恢复逻辑用标题和替换后的正文都核对过。
